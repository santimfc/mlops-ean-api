Del notebook a internet

Cómo convertir un modelo entrenado en Databricks en una página web que cualquier persona puede usar, desplegando una API en Azure con Docker y GitHub Actions.

La arquitectura que vamos a construir

El proyecto tiene tres recorridos que se cruzan. Cada uno es una línea del mapa: el modelo nace en Databricks, el código viaja desde tu computador hasta Azure, y la predicción va del usuario al modelo y de vuelta.

Modelo (Databricks) Código (tu PC → GitHub → Azure) Predicción (usuario → modelo)

Las estaciones con contorno oscuro son correspondencias: la API es donde llega el código y por donde pasa la predicción; el endpoint es donde llega el modelo y donde termina la predicción.

Qué hace cada pieza

PiezaDónde viveQué hace

Endpoint MLOPS_EANDatabricks, Model ServingMantiene el modelo encendido y responde predicciones por internet, protegido con un token.

GitHub ActionsGitHubCada vez que subes cambios, construye la imagen Docker y la despliega en Azure.

Página index.htmlAzure Storage stmlopseanlpEl formulario que ve el usuario.

El viaje de una predicción

  1. El usuario abre la página web, llena los 7 datos del estudiante y hace clic en Predecir.
  2. La página envía esos datos a la API en Azure, a la ruta /predecir.
  3. La API revisa que los datos tengan sentido (por ejemplo, que la asistencia esté entre 0 y 100) y los pone en el formato que exige Databricks.
  4. La API llama al endpoint MLOPS_EAN mostrando el token, como quien muestra el carné en la portería.
  5. Databricks ejecuta el modelo champion y responde {"predictions": [1]}.
  6. La API traduce el 1 a "Aprueba" y se lo devuelve a la página, que lo muestra como un sello verde.

Por qué está diseñado así

El modelo y la API viven separados. El modelo se queda en Databricks, que es donde se entrena, se versiona y tiene instaladas sus librerías. La API en Azure no carga el modelo: solo hace de mensajera. Esto trae tres ventajas:

  • Reentrenar no obliga a tocar Azure. Si el modelo cambia, se actualiza el endpoint en Databricks; la API sigue llamando a la misma dirección.
  • El Docker es liviano. No necesita scikit-learn ni pandas, solo tres librerías.
  • Hay un solo lugar de verdad para el modelo: MLflow en Databricks.

Analogía

Piensa en un restaurante. La cocina (Databricks) prepara los platos y tiene todos los ingredientes. El mesero (la API) toma el pedido del cliente, lo lleva a la cocina y trae el plato. El menú (index.html) es lo que el cliente ve. Si el chef cambia la receta, el mesero no necesita aprender a cocinar.

El costo de este diseño

Si el endpoint de Databricks se cae o está apagado, la API también falla. Databricks Free Edition no garantiza disponibilidad, así que esto sirve para aprender y para prototipos, no para un servicio crítico.

Conceptos clave

Antes de empezar, estas son las palabras que vas a escuchar durante toda la práctica.

Endpoint de Model Serving
Un modelo "encendido" con una dirección web propia. Recibe datos y devuelve predicciones. Sin endpoint, el modelo solo existe guardado en el catálogo.
Alias champion
Una etiqueta que apunta a una versión del modelo. Hoy @champion apunta a la versión 4; si mañana promueves la 5, la etiqueta se mueve.
Token
Una contraseña larga (empieza con dapi) que demuestra que quien llama al endpoint tiene permiso.
API
Un programa que recibe peticiones por internet y responde. La nuestra está hecha con FastAPI y tiene dos rutas: /health (¿estás viva?) y /predecir.
Docker, imagen y contenedor
Docker empaqueta un programa con todo lo que necesita para correr. La imagen es el paquete cerrado; el contenedor es ese paquete funcionando. Así la API corre igual en tu computador y en Azure.
Container Registry
Una bodega de imágenes Docker en Azure. GitHub Actions deja ahí cada versión de la API.
Container Apps
El servicio de Azure que toma una imagen y la pone a correr con una URL pública. Se apaga sola cuando nadie la usa.
Git y GitHub
Git guarda versiones de tu código en tu computador. GitHub es el sitio web donde se publican esas versiones.
GitHub Actions
Un robot de GitHub que ejecuta tareas automáticamente cuando subes código. Aquí construye la imagen y la despliega.
Secretos
Valores sensibles (token, credenciales) que se guardan en GitHub o Azure de forma oculta, para que nunca queden escritos en el código.
Azure CLI
Un programa para manejar Azure escribiendo comandos que empiezan con az, en lugar de hacer clics en el portal. Los comandos se pueden copiar, repetir y automatizar.
Grupo de recursos
Una carpeta en Azure que agrupa todo lo del proyecto. Borrarla borra todo lo que contiene.
Región
El centro de datos físico donde se crean los recursos (por ejemplo westus). Las cuentas Azure for Students solo permiten algunas regiones.
Proveedor de recursos
Cada servicio de Azure (Container Apps, Storage…) debe activarse en una suscripción nueva antes de usarse. Activarlo se llama "registrar el proveedor".
CORS
Una regla de seguridad del navegador. Como la página y la API están en direcciones distintas, la API debe autorizar explícitamente que la página la llame.

Fase 0Databricks: poner el modelo a responder

El punto de partida es un modelo ya entrenado y registrado en Unity Catalog con el alias @champion. En esta fase lo convertimos en un servicio que responde por internet.

1. Confirmar cuál es el champion

En un notebook de Databricks:

Python · notebook de Databricks
import mlflow
from mlflow.tracking import MlflowClient

MODEL_NAME = "workspace.default.mlops-posgrado-estudiantes"  # nombre en Unity Catalog
client = MlflowClient()

champ = client.get_model_version_by_alias(MODEL_NAME, "champion")  # versión con alias champion
print(f"Champion = versión {champ.version}")

info = mlflow.models.get_model_info(f"models:/{MODEL_NAME}@champion")  # firma: campos que espera
print(info.signature)

Debe imprimir la versión (en nuestro caso, 4) y la firma con los 7 campos de entrada. La firma es el contrato de lo que el modelo espera recibir: nombres de columnas y tipos.

Comprueba

"Champion = versión 4" significa que el alias apunta a esa versión. En el formulario de Serving no aparece el alias, solo números: por eso eliges la versión 4.

2. Crear el endpoint

  1. Menú izquierdo → Serving → Create serving endpoint.
  2. Name: MLOPS_EAN.
  3. Entity: workspace.default.mlops-posgrado-estudiantes, versión 4.
  4. Compute: CPU, tamaño Small, con Scale to zero activado (se apaga cuando nadie lo usa).
  5. Create y espera unos minutos hasta que el estado sea Ready.

¿Cómo sabe el endpoint qué librerías usar?

Cuando registraste el modelo con MLflow, se guardaron junto a él un requirements.txt y un conda.yaml con las versiones exactas de scikit-learn, pandas y Python. El endpoint los lee y monta un entorno idéntico al del entrenamiento. Puedes verlos en Catalog → modelo → versión 4 → Artifacts.

3. Generar el token

  1. Clic en tu usuario (arriba a la derecha) → Settings → Developer → Access tokens → Generate new token.
  2. Ponle un comentario y una duración de 90 días.
  3. Copia el valor dapi... y guárdalo: Databricks no lo vuelve a mostrar.

4. Probar el endpoint

La URL del endpoint aparece en Serving → MLOPS_EAN, y termina en /serving-endpoints/MLOPS_EAN/invocations. Prueba desde una celda de Python:

Python · prueba del endpoint
import requests

URL = "https://TU_WORKSPACE.cloud.databricks.com/serving-endpoints/MLOPS_EAN/invocations"
TOKEN = "dapi..."  # tu token

# datos de un estudiante de prueba, en el formato que exige Databricks
datos = {"dataframe_records": [{
    "horas_estudio": 7.5, "horas_sueno": 7.0, "asistencia": 90.0,
    "promedio_previo": 4.2, "indice_dedicacion": 8.0,
    "en_riesgo": 0, "destacado": 1
}]}

r = requests.post(URL, headers={"Authorization": f"Bearer {TOKEN}"}, json=datos, timeout=120)  # timeout largo por el arranque en frío
print(r.status_code)  # 200 = OK
print(r.json())       # {'predictions': [1]}

Este código es exactamente lo que la API hará por dentro: mandar los datos con el token y leer la respuesta.

Resultado esperado

200 y {'predictions': [1]}. El 1 significa que el modelo predice que el estudiante aprueba.

5. El endpoint queda fijo en una versión

El endpoint guarda el número de versión, no el alias. Si reentrenas y la versión 5 pasa a ser champion, el endpoint sigue sirviendo la 4 hasta que alguien lo actualice.

Analogía

El mesero tiene anotado "entregar el plato número 4". Si la cocina prepara un plato nuevo y le pone la etiqueta "champion", nadie le avisa al mesero. Hay que decirle: "ahora entrega el que tenga la etiqueta champion".

Ese aviso se puede hacer a mano (Serving → Edit endpoint → cambiar la versión) o con esta celda al final del notebook que promueve el champion:

Python · al final de NB03
from databricks.sdk import WorkspaceClient
from databricks.sdk.service.serving import ServedEntityInput

w = WorkspaceClient()  # dentro de Databricks se autentica solo
version = client.get_model_version_by_alias(MODEL_NAME, "champion").version  # versión champion actual

w.serving_endpoints.update_config_and_wait(
    name="MLOPS_EAN",
    served_entities=[ServedEntityInput(
        entity_name=MODEL_NAME,
        entity_version=str(version),  # le dice al endpoint qué versión servir
        workload_size="Small",
        scale_to_zero_enabled=True,
    )],
)
print(f"MLOPS_EAN ahora sirve la versión {version}")

La celda hace los mismos cuatro pasos que harías a mano: averigua la versión del champion, edita el endpoint, cambia el número y espera a que quede listo. Mientras se actualiza, el endpoint sigue sirviendo la versión anterior, así que la API no se cae.

main.py

main.py
# API FastAPI que recibe los datos de un estudiante y consulta el endpoint MLOPS_EAN de Databricks
import os
import requests
from fastapi import FastAPI, HTTPException
from fastapi.middleware.cors import CORSMiddleware
from pydantic import BaseModel, Field

# Credenciales: se inyectan como variables de entorno en Azure (nunca escritas en el código)
DATABRICKS_URL = os.getenv("DATABRICKS_URL")
DATABRICKS_TOKEN = os.getenv("DATABRICKS_TOKEN")

app = FastAPI(title="API MLOps EAN", description="Predicción de aprobación de estudiantes")

# Permite que el frontend (index.html) llame a la API desde otro dominio
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_methods=["*"], allow_headers=["*"])


# Campos que espera el modelo (deben coincidir con la firma registrada en MLflow)
class Estudiante(BaseModel):
    horas_estudio: float = Field(..., ge=0, le=24)
    horas_sueno: float = Field(..., ge=0, le=24)
    asistencia: float = Field(..., ge=0, le=100)
    promedio_previo: float = Field(..., ge=0, le=5)
    indice_dedicacion: float = Field(..., ge=0)
    en_riesgo: int = Field(..., ge=0, le=1)
    destacado: int = Field(..., ge=0, le=1)


@app.get("/health")
def health():
    # Verifica que la API está viva y que tiene configuradas las credenciales
    return {"status": "ok", "databricks_configurado": bool(DATABRICKS_URL and DATABRICKS_TOKEN)}


@app.post("/predecir")
def predecir(est: Estudiante):
    if not (DATABRICKS_URL and DATABRICKS_TOKEN):
        raise HTTPException(status_code=500, detail="Faltan DATABRICKS_URL o DATABRICKS_TOKEN")

    # Databricks exige el formato dataframe_records
    payload = {"dataframe_records": [est.model_dump()]}

    try:
        r = requests.post(
            DATABRICKS_URL,
            headers={"Authorization": f"Bearer {DATABRICKS_TOKEN}"},
            json=payload,
            timeout=120,  # margen para el arranque en frío del endpoint
        )
    except requests.exceptions.Timeout:
        raise HTTPException(status_code=504, detail="Databricks tardó demasiado (arranque en frío). Intente de nuevo.")

    if r.status_code != 200:
        raise HTTPException(status_code=502, detail=f"Error de Databricks: {r.text}")

    pred = int(r.json()["predictions"][0])  # 1 = aprueba, 0 = reprueba
    return {
        "prediccion": pred,
        "resultado": "Aprueba ✅" if pred == 1 else "Reprueba ❌",
        "datos_recibidos": est.model_dump(),
    }

Por partes:

  • Credenciales desde el entorno. os.getenv lee la URL y el token que Azure le inyecta. No están escritos en el código, así que el repositorio puede ser público sin riesgo.
  • CORS abierto. Permite que la página en Storage, que está en otra dirección, pueda llamar a la API.
  • La clase Estudiante. Define los 7 campos, su tipo y su rango. Si alguien envía asistencia: 150, la API lo rechaza con un error 422 antes de molestar a Databricks.
  • /health. Ruta de diagnóstico: confirma que la API está viva y que tiene la URL y el token configurados.
  • /predecir. Pone los datos en formato dataframe_records, llama al endpoint con el token, y traduce el 1 o 0 a texto. Si Databricks tarda demasiado responde 504; si Databricks falla, 502.

requirements.txt

requirements.txt

¿Cómo se sabe qué poner aquí? Sale de lo que el programa hace. La API tiene tres trabajos, y cada uno necesita una herramienta:

TrabajoLibreríaDónde se ve
Recibir peticiones de internetfastapifrom fastapi import FastAPI
Estar encendida y escuchandouvicornEn el Dockerfile: CMD ["uvicorn", ...]

La regla práctica: revisa los import de tu código. Lo que viene con Python (os, json, datetime…) no va; lo que instalaste con pip sí. Las versiones se fijan con == para que la imagen se construya siempre igual; puedes verlas con pip show fastapi uvicorn requests.

No van las librerías del modelo

scikit-learn y pandas no están aquí porque el modelo no corre en el Docker: corre en el endpoint de Databricks, que tiene su propio entorno. Son dos entornos separados.

Dockerfile

Dockerfile
# Imagen base liviana de Python
FROM python:3.11-slim

WORKDIR /app

# Instalar dependencias primero (aprovecha la caché de Docker)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copiar el código de la API
COPY main.py .

# Container Apps enviará el tráfico a este puerto
EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
InstrucciónQué significa
FROM python:3.11-slim"Dame un Linux con Python 3.11 ya instalado." slim es la versión liviana.
WORKDIR /app"Crea la carpeta /app y trabaja dentro de ella."
COPY requirements.txt . + RUN pip install"Copia la lista de librerías e instálalas."
COPY main.py ."Copia el código." El contenedor empieza vacío: tus archivos no existen dentro hasta que se copian.
EXPOSE 8000"La API atiende por la puerta 8000."
CMD [...]"Al encender, arranca la API con Uvicorn." 0.0.0.0 acepta conexiones desde fuera del contenedor.

¿Por qué se copia requirements.txt antes que main.py?

Docker guarda en caché cada paso. Las librerías cambian poco y tardan en instalarse; el código cambia seguido. Con este orden, si editas main.py, Docker reutiliza la instalación y solo repite la última copia. La construcción tarda segundos en lugar de minutos.

Fase 4Despliegue automático con GitHub Actions

La idea: cada vez que hagas git push, GitHub construye la imagen Docker y la pone a correr en Azure, sin que entres al portal.

1. Crear una identidad para GitHub

GitHub no puede iniciar sesión con tu usuario. Necesita una "cuenta de servicio" propia, con permiso solo sobre el grupo rg-mlops-ean:

Anaconda Prompt
az ad sp create-for-rbac --name sp-mlops-ean-github --role contributor --scopes /subscriptions/TU_SUBSCRIPTION_ID/resourceGroups/rg-mlops-ean --json-auth

Responde un JSON con varias líneas. Para GitHub solo necesitas estos cuatro campos:

AZURE_CREDENTIALS
{
  "clientId": "...",
  "clientSecret": "...",
  "subscriptionId": "...",
  "tenantId": "..."
}

El clientSecret es una contraseña

Da acceso a tu grupo de recursos. No lo pegues en chats, documentos ni en el código; solo en el secreto de GitHub.

2. Cargar los secretos en GitHub

En el repositorio: Settings → Secrets and variables → Actions → New repository secret. Si no ves Settings, está en el menú "…" a la derecha de las pestañas.

NameSecret
AZURE_CREDENTIALSEl JSON de 4 campos, completo

DATABRICKS_TOKENEl token dapi...

Los nombres deben ir exactamente así, porque el workflow los busca por nombre. GitHub nunca vuelve a mostrar el valor: es normal.

3. El archivo del workflow

Guárdalo en esta ruta exacta dentro de tu carpeta:

Ruta
C:\mlops-ean-api\.github\workflows\deploy.yml
deploy.yml
# Despliegue automático de la API en Azure Container Apps
# Se ejecuta en cada push a main (excepto si solo cambia index.html) o a mano desde la pestaña Actions
name: Desplegar API en Azure

on:
  push:
    branches: [main]
    paths-ignore: ["index.html"]   # el frontend vive en Storage, no requiere reconstruir el Docker
  workflow_dispatch:

env:
  RESOURCE_GROUP: rg-mlops-ean
  ACR_NAME: acrmlopseanlp
  ENVIRONMENT: env-mlops-ean
  APP_NAME: api-mlops-ean
  IMAGE: acrmlopseanlp.azurecr.io/api-mlops-ean:${{ github.sha }}   # cada versión con la etiqueta del commit

jobs:
  desplegar:
    runs-on: ubuntu-latest
    steps:
      # 1. Descarga el código del repositorio
      - uses: actions/checkout@v4

      # 2. Inicia sesión en Azure con la cuenta de servicio
      - uses: azure/login@v2
        with:
          creds: ${{ secrets.AZURE_CREDENTIALS }}

      # 3. Construye la imagen Docker y la sube al Container Registry
      - name: Construir y subir imagen
        run: |
          az acr login --name $ACR_NAME
          docker build -t $IMAGE .
          docker push $IMAGE

      # 4. Crea la Container App la primera vez; las siguientes solo la actualiza
      - name: Crear o actualizar la API
        env:
          DB_URL: ${{ secrets.DATABRICKS_URL }}
          DB_TOKEN: ${{ secrets.DATABRICKS_TOKEN }}
        run: |
          if az containerapp show -n $APP_NAME -g $RESOURCE_GROUP > /dev/null 2>&1; then
            echo "La API ya existe: se actualiza"
            az containerapp secret set -n $APP_NAME -g $RESOURCE_GROUP \
              --secrets databricks-url="$DB_URL" databricks-token="$DB_TOKEN"
            az containerapp update -n $APP_NAME -g $RESOURCE_GROUP --image $IMAGE
          else
            echo "Primera vez: se crea la API"
            ACR_PASSWORD=$(az acr credential show -n $ACR_NAME --query "passwords[0].value" -o tsv)
            az containerapp create -n $APP_NAME -g $RESOURCE_GROUP \
              --environment $ENVIRONMENT \
              --image $IMAGE \
              --registry-server $ACR_NAME.azurecr.io \
              --registry-username $ACR_NAME \
              --registry-password "$ACR_PASSWORD" \
              --target-port 8000 \
              --ingress external \
              --min-replicas 0 \
              --max-replicas 1 \
              --secrets databricks-url="$DB_URL" databricks-token="$DB_TOKEN" \
              --env-vars DATABRICKS_URL=secretref:databricks-url DATABRICKS_TOKEN=secretref:databricks-token
          fi

      # 5. Muestra la URL pública de la API
      - name: URL de la API
        run: |
          FQDN=$(az containerapp show -n $APP_NAME -g $RESOURCE_GROUP --query properties.configuration.ingress.fqdn -o tsv)
          echo "API publicada en: https://$FQDN"
          echo "Pruebe: https://$FQDN/health"

Lo que hace, en orden:

  1. Descarga el código del repositorio.
  2. Entra a Azure con la cuenta de servicio de AZURE_CREDENTIALS.
  3. Construye la imagen con el Dockerfile y la sube al registry, etiquetada con el código del commit. Así cada versión queda identificada.
  4. Crea la API la primera vez, o la actualiza las siguientes. La URL y el token de Databricks entran como secretos de Container Apps (secretref), nunca como texto visible.
  5. Imprime la URL pública de la API.

Dos decisiones importantes: si solo cambia index.html, el workflow no se dispara, porque la página vive en Storage. Y --min-replicas 0 apaga la API cuando nadie la usa, para no gastar crédito.

Fase 5Probar la API

Con la URL que imprimió el workflow (algo como https://api-mlops-ean.xxxx.westus.azurecontainerapps.io):

1. ¿Está viva?

Abre en el navegador https://TU_URL/health. Debe responder:

{"status": "ok", "databricks_configurado": true}

Si databricks_configurado sale false, los secretos de Databricks no llegaron a la API.

2. La documentación automática

FastAPI genera una página de pruebas en https://TU_URL/docs. Ahí puedes abrir /predecir, hacer clic en Try it out, escribir los datos y ejecutar. Es la forma más visual de mostrarla en clase.

3. Desde Python

Python
import requests

URL = "https://TU_URL/predecir"

datos = {
    "horas_estudio": 7.5, "horas_sueno": 7.0, "asistencia": 90.0,
    "promedio_previo": 4.2, "indice_dedicacion": 8.0,
    "en_riesgo": 0, "destacado": 1
}

r = requests.post(URL, json=datos, timeout=120)
print(r.status_code)  # 200
print(r.json())       # {'prediccion': 1, 'resultado': 'Aprueba ✅', ...}

Fíjate en la diferencia con la prueba de la Fase 0: aquí no hay token ni dataframe_records. La API se encarga de eso; el usuario solo envía los datos del estudiante.

Cuando algo cambia

La gran ventaja de esta arquitectura es que cada tipo de cambio tiene su propio camino, y ninguno obliga a rehacer todo.

Qué cambiaQué hacesQué no se toca
El modelo (reentrenamiento por drift)NB02 reentrena, NB03 promueve el champion y actualiza el endpointGitHub, Docker, Azure
El código de la APIEditas main.py y haces git add, commit, pushDatabricks, la página
Una librería de la APIEditas requirements.txt y haces pushDatabricks, la página
El diseño de la páginaEditas index.html y lo vuelves a subir al StorageLa API, Databricks
El token de Databricks venceGeneras uno nuevo, actualizas el secreto DATABRICKS_TOKEN en GitHub y relanzas el workflowEl código

El ciclo completo de MLOps queda así:

NB04 detecta drift → NB02 reentrena → NB03 promueve champion + actualiza MLOPS_EAN
                                                     ↓
                     La API en Azure sigue llamando a la misma URL y ya usa el modelo nuevo

Para relanzar el workflow sin cambiar código: pestaña Actions → Desplegar API en Azure → Run workflow.

Al terminar el curso: borrar todo

El Container Registry cobra unos pocos dólares al mes aunque no se use. Para no gastar el crédito, borra el grupo completo; se lleva todos los recursos de Azure:

Anaconda Prompt
az group delete --name rg-mlops-ean --yes

Y en Databricks, borra el endpoint MLOPS_EAN desde Serving y revoca el token en Settings → Developer → Access tokens.
